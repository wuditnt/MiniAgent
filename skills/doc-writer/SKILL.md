# 文档写作

目标：把零散需求与素材，写成读者能直接读懂、能直接存档的文档。

## 适用与不适用

- 适用：需求说明、方案设计、操作手册、对外介绍、项目总结。
- 不适用：数据分析（用 CSV 分析）、纯代码修改、会议记录整理（用会议纪要）。

## 第 0 步：确认要素

只问真正影响结构的项，一次问完（`ask_user`，选项 ≤ 4 个）：

1. 交付格式：Markdown / Word；
2. 读者：内部同事 / 客户 / 新人；
3. 篇幅：一页摘要 / 完整章节。

用户已在需求里说明的不要再问。

## 步骤

1. **收集素材**：`list_dir` 看目录，`read_file` / `read_docx` / `read_pdf` 读已有材料；
   需要外部事实时用 `web_search`，读原文用 `fetch_url`，并记下来源与日期。
2. **先列大纲**：3–6 个一级标题，第一个是执行摘要（结论先行）。大纲先给用户看，一句话确认后再展开。
3. **写正文**：每节先给结论，再给依据；步骤写成有序列表；术语首次出现给一句定义。
4. **落盘**：Markdown 存 `docs/<主题>.md`；需要 Word 时用 `write_docx` 存 `docs/<主题>.docx`。
5. **自查**后把文件路径告诉用户。

## 输出规范

- 标题层级最多三级，不用「以下是」「综上所述」这类空话开头。
- 对比信息用 GFM 表格；代码、命令、配置用带语言标记的代码块。
- 数字与引用必须标来源；拿不到就写「未获取」，不要估。

## 自检清单

- [ ] 执行摘要里能读到最终结论
- [ ] 每个结论都有依据（数据 / 来源 / 代码位置）
- [ ] 术语前后一致，缩写首次出现有解释
- [ ] 文件已落盘，路径正确

## 约束

- 不编造数据、链接、引用。
- 不覆盖用户已有文件：同名时加 `-v2` 后缀。
- 用户只要内容不要文件时，直接在对话里给全文，不落盘。
