# 技术方案写作

目标：让评审者不用追问，就能判断「做不做、怎么做、代价与风险」。

## 适用与不适用

- 适用：架构设计、RFC、技术选型、重构 / 迁移 / 兼容方案、接口与数据模型设计。
- 不适用：面向用户的说明书（用「通用文档写作」）、纯资料调研（用「调研简报」）、
  直接改代码。

## 第 0 步：确认评审口径

用 `ask_user` 一次问完，用户已说明的跳过：

1. 读者与决策人：同组评审 / 跨团队 / 管理层；
2. 评审要回答的核心问题：能不能做 / 选哪个 / 怎么分期；
3. 交付格式：Markdown / Word。

没说明时按「跨团队评审、能不能做、Markdown」默认，不要反复追问。

## 步骤

1. **核实现状**（不凭印象）：
   - `glob_files` / `list_dir` 定位模块，`grep` 找调用点，`read_file` 读关键实现；
   - 每条现状记录 `path:line`、现有行为、约束（性能 / 兼容 / 依赖）；
   - 涉及外部能力用 `web_search`、`fetch_url`，记录来源与日期。
2. **定边界**：目标写成可验证的验收口径；单列「非目标」与关键假设。
3. **设计方案**：总体架构 → 模块职责 → 接口 / 数据模型 → 关键流程
   （必要时用 Mermaid）→ 失败路径与降级。
4. **选型对比**：至少 2 个可行选项，用 GFM 表格列「做法 / 收益 / 代价 / 结论」，
   并说明为什么不是另一个。
5. **风险与权衡**：兼容性、迁移步骤、回滚、监控、成本，每条给缓解措施。
6. **验证与交付**：测试口径（单测 / 集成 / 压测）、分阶段里程碑（不写日期承诺）。
7. **落盘**：Markdown 存 `docs/<主题>-方案.md`（`write_file`）；
   需要 Word 时用 `write_docx` 存 `docs/<主题>-方案.docx`。
8. **自查**后给出文件路径，并补一句「评审建议先看哪三处」。

## 输出规范

- 结论先行：开头 5 行内给出推荐方案与它的主要代价。
- 现状判断必须带 `path:line`；拿不到证据写「未确认」，不要估。
- 术语前后一致，缩写首次出现给定义。
- 不用「大概 / 可能 / 建议考虑」，改成明确条件与取舍。

## 自检清单

- [ ] 目标可验收，且写清了非目标
- [ ] 每个设计结论都能追到代码位置或数据
- [ ] 选型至少两个选项，有明确结论
- [ ] 风险都有缓解措施与回滚路径
- [ ] 文件已落盘，路径正确

## 约束

- 不编造代码位置、数据、链接。
- 不覆盖用户已有文件：同名时加 `-v2` 后缀。
- 只出方案，不顺手改业务代码；接口签名 / 伪代码可以写。
