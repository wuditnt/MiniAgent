# 日志排错

目标：从「报错了」走到「根因是这行代码，这样改」。

## 适用与不适用

- 适用：应用日志、构建报错、接口 5xx、崩溃堆栈、超时排查。
- 不适用：需要线上实时权限的排障；没有日志时凭感觉猜原因。

## 步骤

1. **摸清材料**：`list_dir` / `glob_files` 找日志文件，`read_file` 读；
   文件大就用 `grep` 先筛 `ERROR|FATAL|Exception|Traceback|timeout`。
2. **锁时间窗**：按时间戳找异常开始的那一刻，记录第一条错误（不是最响的那条）。
3. **串调用链**：用同一个 trace id / request id / 用户 id 串起前后日志，还原请求路径。
4. **区分症状与根因**：下游的「连接被拒绝」往往是上游先挂；找最早出现的异常。
5. **验证**：能复现就用 `run_shell` / `run_python` 跑最小命令；
   涉及项目代码时先 `grep` / `read_file` 看实现，再下结论。
6. **给结论**：根因 → 证据（文件:行号 / 时间戳）→ 修复建议 → 如何验证修好了。

## 输出结构

```markdown
## 结论
根因一句话。

## 证据
- 2026-01-01 10:00:01 ERROR …（logs/app.log:1288）
- 代码：src/xxx.py:42 未处理 None

## 修复
1. ……

## 验证
- 复现命令：……
- 期望结果：……
```

## 输出规范

- 引用日志 ≤ 30 行，只贴关键片段，标注来源文件与行号。
- 多条可能原因时按可能性排序，并说明各自的验证方式。
- 用户要报告时写 `reports/<主题>-排错.md`。

## 约束

- 不整篇粘贴日志。
- 不臆测第三方库或接口行为：先查文档 / 源码 / 实际返回。
- 不确定的结论明确标「待验证」，不要包装成确定答案。
